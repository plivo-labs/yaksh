---
title: Outbound agents
description: Do tests of an agent that calls Yaksh.
---

An outbound agent calls Yaksh. Yaksh sends the trigger of the agent: a POST or GET request that makes the agent call one of the Yaksh numbers. Then Yaksh answers the call.

## Prepare for outbound tests

1. On the **Phone** tab of Settings, choose the receiving application. Click **Make application**, or choose an application of the account. The answer URL of the application must be `<YAKSH_PUBLIC_URL>/incoming` and its hangup URL `<YAKSH_PUBLIC_URL>/incoming/hangup`, both with the method `POST`. Refer to [Phone numbers](/docs/configuration#phone-numbers).
2. On the **Numbers** page, click **Use for tests** on each number that gets test calls.
3. Add an agent with the direction `outbound`. Give the method, the URL and the headers of its trigger. A POST trigger has a JSON body (`body`). A GET trigger has query parameters (`query`), a list of names and values, and no body. In the Yaksh console, choose **The agent** under **Who starts the conversation?** and select **Phone**. Then complete the fields in **Start request**.

The worker reads the numbers of the account again every 5 minutes by default, and at once when you click **Refresh** on the **Numbers** page. You do not restart the worker after a change in the Plivo console. If `YAKSH_PUBLIC_URL` changes, fix the URLs of the receiving application on the **Phone** tab of Settings. If outbound tests are off, the **Numbers** page shows the cause.

## Trigger

The trigger URL must use `https` and a public address. Yaksh saves an `http` URL, but each test then stops with the end reason `trigger_failed`. For an agent on your own network, set `YAKSH_ALLOW_PRIVATE_HOSTS`.

The dial window (`dial_window_s`) is the time that Yaksh waits for the call of the agent: 10 to 600 seconds. The default is 120. The wait starts when Yaksh gets a number for the conversation. Yaksh adds 15 seconds for the trigger request. If no call comes during this time, the conversation stops with the end reason `no_call`. If you give calling numbers (`calling_numbers`), Yaksh accepts a call only from these numbers.

## Placeholders

You can put placeholders in header values, in the string values of the JSON body and in the values of query parameters. The URL, the names of the JSON fields and the names of query parameters cannot have placeholders. Yaksh encodes each query value and adds the parameters after the query that the URL already has.

| Placeholder | Value |
| --- | --- |
| `{{yaksh.number}}` | The number that the agent must call. |
| `{{yaksh.conversation_id}}` | The ID of the conversation. |
| `{{agent_data.<name>}}` | A value from the agent data of the data set the call plays. |
| `{{secrets.<NAME>}}` | A trigger secret from the **Phone** tab of Settings. `<NAME>` has only uppercase letters, digits and underscores, and starts with a letter. |

Agent data is a list of names and values in a scenario. Yaksh sends it only in the trigger. The caller does not get it. Each scenario must have each agent data name that the trigger uses. If not, Yaksh rejects the request. For a run, Yaksh starts no conversation.

Do not put the value of a secret in a trigger: Yaksh keeps the headers and the body of a trigger in the database without encryption. Save the secret in Settings and use `{{secrets.<NAME>}}`. If Settings has no trigger secret that the trigger uses, the conversation stops with the end reason `trigger_failed`.

## Signed triggers

Each trigger has the header `X-Yaksh-Delivery` with the ID of the conversation. Yaksh sends each trigger only one time. Thus, a second request with the same ID is a replay.

If Settings has a signing key, each trigger also has these headers. To make the key, click **Generate key** on the **Phone** tab of Settings. Yaksh shows the key one time; copy it to your endpoint.

| Header | Value |
| --- | --- |
| `X-Yaksh-Timestamp` | The time of the request, in Unix seconds. |
| `X-Yaksh-Signature` | `v1=` and then the HMAC-SHA256 of `<X-Yaksh-Delivery>.<X-Yaksh-Timestamp>.<body>` in lowercase hexadecimal. For a GET trigger, the full URL with its query, as your server receives it, takes the place of the body. The key is the signing key from Settings. |

To examine a trigger in your endpoint:

1. Reject the request if its timestamp is more than 5 minutes before or after the time of your clock.
2. Calculate the signature from the bytes of the body that you received, or from the full URL for a GET. Compare it with the header in constant time.
3. Record the delivery ID. Reject a delivery ID that you recorded before.

For the variables of outbound tests, refer to [Configuration](/docs/configuration#environment-variables).
